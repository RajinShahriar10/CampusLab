1. What Final Term Week 1 must deliver
Submission 3 is JavaScript functionality, including client-side form validation. In Week 5 we built the pages and forms, and in Week 6 we styled them. This week the pages start to behave: every form checks what the user typed and shows a clear message next to each wrong field, and every page gets a few working features (filtering, live counters, tables built from data, confirmation questions).
Why validation is only half the story: client-side checks help the user fix mistakes quickly, but anyone can switch JavaScript off or send data without our page. In the PHP weeks (Final Term Weeks 3-4) every rule written this week must be checked again on the server. Keep your rules written clearly so they are easy to copy there.
Scope
In scope (this week)
JavaScript for all 27 pages, written in external .js files: validation of every form (required fields, formats, lengths, dates and times, file type and size, matching passwords, required choices), error and success messages, and the extra features listed for each page in Sections 8-11. Small HTML additions to connect the scripts: <script src> tags, error <span>s, onsubmit/onclick calls, novalidate.
Not this week
PHP, MVC, sessions and database (Final Term Weeks 3-4). Real data: sample data lives in arrays in our JS files. Libraries and frameworks (jQuery, React...) and anything the course has not taught: fetch, localStorage, async, classes. New pages or new form fields, and any change to a field name (names become $_POST keys).
Must run as submitted
Opening index.html and using every page must work with no red errors in the browser console (F12). Every form shows messages for wrong input, and shows a success message for correct input. No code is written inside HTML <script> tags.

5.1 How validation works on every page

5.2 Linking the scripts
Put the script tags at the very end of <body> (so the page elements exist when the code runs). validation.js always comes first, then your role file. Pages inside a folder go up one level to reach js/:
        </div>
    </div>
    <script src="../js/validation.js"></script>
    <script src="../js/student.js"></script>
</body>
If the console says showError is not defined, the first line is missing, has a wrong path, or comes after your own file.
5.3 Form markup pattern
Add four things to each form, and change nothing else: novalidate and onsubmit on the <form>, and one error <span> right after the <br /> of every field that is validated. The span id is always the field's id plus -error.
<form action="#" method="post" onsubmit="return validateRegister(this)" novalidate>
    <fieldset>
        <legend>Personal Details</legend>
        <label for="email">Email:</label>
        <input type="email" id="email" name="email" placeholder="Enter your email" required />
        <br />
        <span class="error" id="email-error"></span>
        ...
    </fieldset>
</form>
For a group of radio buttons the span id is the group name plus -error (for example severity-error). For fields inside a table row, the field id already has the row id in it (new-date-101), so its span is new-date-101-error.

5.4 Writing JavaScript the way the course teaches it
We copy the style from the faculty's Lab 5 examples. This is what one complete validation function looks like (it is the pattern for every form):
function validateLogin (form) {
    let loginId = document.getElementById("login-id").value;
    let password = document.getElementById("password").value;
    let valid = true;
 
    clearErrors();
    if (isEmpty(loginId)) {
        showError("login-id", "Email or student ID is required");
        valid = false;
    } else if (!isEmail(loginId) && !isStudentId(loginId)) {
        showError("login-id", "Enter a valid email or a student ID like 24-57561-2");
        valid = false;
    }
    if (password.length < 8) {
        showError("password", "Password must be at least 8 characters");
        valid = false;
    }
    return finishForm(valid, form);
}
Layout: tab indentation, let for variables, function name () {, double quotes, a semicolon at the end of every statement, one short // comment where something is not obvious (the way the faculty comments querySelectorAll).
Names: camelCase. Validation functions are validate + the form (validateRegister, validateBooking). Feature functions say what they do (filterEquipment, showWorkload).
Only use what the course has taught: getElementById, querySelector, querySelectorAll, createElement, appendChild, innerText, innerHTML, element.style, value, length, if / else, for, for...of, forEach, arrays of objects, object properties, and the basics from w3schools (trim(), includes(), Date, alert(), confirm(), regular expressions with test()).
Not allowed: libraries, fetch, localStorage, async, classes, and arrow functions. Write function (card) { ... }, not card => ....
Do not copy-paste a check that a helper already does. If a check is missing from validation.js, ask the leader.
console.log() is fine while testing (the faculty uses it too). Delete it before your pull request.

5.7 Rules
Every form gets validation, even when its fields are optional: check formats and lengths of whatever the user did type.
Check every field, not just the first wrong one. All wrong fields show a message at the same time. The first wrong field receives the cursor.
Messages disappear the next time the user submits (call clearErrors() first) and the red border goes with them.
Valid input shows a green success message and does not reload the page. Do not use alert() for validation messages; alert() and confirm() are only for confirmations ("Delete this lab?").
Destructive actions (delete, cancel, deactivate, delete account) keep their confirm checkbox from Week 5 and also ask confirm("...") before going ahead.
Do not trust the page layout: read values from the form fields, never from text on the screen, except for the table features that are about the table itself.
One function per form, one function per feature. A function longer than about 40 lines should be split.
No new features beyond the table in your section. If you have a good idea, tell the leader.

A starting example in the course style
This function (in js/student.js) is the live filter of the catalogue page. It follows the faculty's Lab 5 pattern: select elements, loop over them with forEach, change style. The HTML needs oninput="filterEquipment()" on search, onchange="filterEquipment()" on both selects, and data-lab and data-category on every .equipment-card.
function filterEquipment () {
    let search = document.getElementById("search").value.toLowerCase();
    let lab = document.getElementById("lab-id").value;
    let category = document.getElementById("category").value;
    let cards = document.querySelectorAll(".equipment-card");
    let shown = 0;
 
    // querySelectorAll gives a list, so we can loop over it with forEach
    cards.forEach(function (card) {
        let matchSearch = card.innerText.toLowerCase().includes(search);
        let matchLab = lab == "" || card.getAttribute("data-lab") == lab;
        let matchCategory = category == "" || card.getAttribute("data-category") == category;
        if (matchSearch && matchLab && matchCategory) {
            card.style.display = "";
            shown++;
        } else {
            card.style.display = "none";
        }
    });
    console.log(shown + " cards shown");
}

This function (in js/admin.js) filters the users table while the admin types in the search box. It loops over the table rows and hides the ones that do not match, the same idea as the catalogue filter. The search field needs oninput="filterUsers()" and the table needs id="users-table".
function filterUsers () {
    let text = document.getElementById("search").value.toLowerCase();
    let rows = document.querySelectorAll("#users-table tr");
    // start from 1 so the header row stays
    for (let i = 1; i < rows.length; i++) {
        if (rows[i].innerText.toLowerCase().includes(text)) {
            rows[i].style.display = "";
        } else {
            rows[i].style.display = "none";
        }
    }
}
